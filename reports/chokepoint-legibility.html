AI Control · Tool-Risk Topology

Naming a tool for its intent can lull the watcher.

Funnelling a possibly-misaligned AI's data exports through one clearly-labeled export_data door was supposed to make misuse easier to catch. A trusted monitor did the opposite: it trusted the sanctioned-sounding name and waved the theft through. The fix isn't a better name — it's removing the one-call escape so the attack is forced to compose, where a monitor can read it.

Method: scripted attacker, 40 variants/design Monitor: llama3.1:8b (local) Stats: catch rate, 95% CI Designs compared: A · B · C · D

The hypothesis we set out to test

A misaligned AI rarely needs a single obviously-dangerous tool — it can compose ordinary ones (read a record here, send a message there) into an exfiltration where every individual step looks benign. The bet: if you carve the tool interface so that every route to a catastrophic effect must pass through one transparent chokepoint, that misuse becomes legible — a trusted monitor can catch it, where a bag of general-purpose tools would let it hide. What follows is what happened when we actually tested that.

The setup

Same powers, three tool designs

An agent gets the identical abilities — read internal data, send data out — through three "carvings" of one tool interface. The question: does the shape of the tools change whether a monitor catches misuse? (A fourth design, D, enters later as the fix.)

A · opaque

One shell command

Everything flows through a single opaque call.

run_command("…")
B · free-form

Many small tools

Typed primitives; "send" is a general external request.

http_request(target, body)
C · chokepoint

Intent tools + one door

One labeled export is the only way data leaves.

export_data(source, dest)

First surprise — the chokepoint backfires

Same stolen data. Two tool names. Opposite verdicts.

Start with the design meant to help — the chokepoint C — against the free-form kit B. We handed the monitor the identical disguised payload of stolen records once as B's generic external request, once as C's call named export_data. Only the label changed.

The theft is byte-for-byte the same. The monitor treats a call named export_data as routine business and lowers its guard — so the one sanctioned door becomes the safest way out.

The measurement

Under a naive monitor, the chokepoint is the worst

40 randomized stealth attacks per design (each verified to reach the sink), scored by a real LLM monitor, catch rate with 95% intervals. C — the design the thesis says is most catchable — caught the fewest.

Fix the monitor — tell it to judge egress by what leaves, not the tool's name (the same instruction for all three designs, never naming the attack) — and C recovers from 11/40 to 36/40. So the collapse was a monitor artifact, not a defect of the chokepoint. But C only reaches parity with B — never beats it.

Why it happens

The label is the vulnerability

A chokepoint concentrates exits

By construction, C forces every possible exfiltration through one door (static analysis: 0 residual paths vs 9 for A and B). Fewer places to watch — that part is real.

…but concentration ≠ scrutiny

Naming the door export_data makes it read as legitimate. A generic http_request to the outside looks sketchy; a labeled "export" looks like normal business. So the monitor watches the one door less, not more.

The benefit of a chokepoint is therefore contingent: it pays off only when paired with a monitor that scrutinizes egress by content and refuses to be reassured by a name. Legibility of intent is not the same as legibility of risk — and it can actively suppress it.

The fix — and the original hypothesis, vindicated

Take away the one-call escape, and the attack must compose

C's real flaw was that its one door accepted an agent-fabricated blob — a single-call escape. Carving D is the same intent-complete toolset with that hole closed: its one egress accepts only a real, named source and stamps that source's class on the call. One small change to the door, shown here:

C · naive chokepoint

export_data

One door — but it accepts agent-composed text, so a disguised blob leaves in a single call. No composition to read.

export_data(source, dest)
source may be text:… ← escape
D · provenance-typed

export_source

Same one door — but the source must be a real object (a file, stored object, or DB query — never agent text), and the call declares that source's class.

export_source(source, dest)
source ∈ file · object · db → declares class

The consequence: to exfiltrate reshaped or attacker-held data, the agent can no longer do it in one call. It must first stage the data into a real source, then export it — a read→write→export composition a monitor can read.

D's rising line is the fingerprint of a forced, legible composition. At a monitor that reads whole trajectories, D catches every attack — matching the conspicuous free-form B and beating the naive chokepoint C. This is the original hypothesis realized: a misaligned agent's tool composition is legible — once the interface refuses to let it skip composing.

Limitations & what we don't claim

Where this result stops

  • One small monitor, modest n. A single 8B trusted monitor, 40 attacks per design. The robust signal is the trend — D's catch rate rises with monitor memory, C's doesn't — not the exact percentages. (An early 6-attack pilot pointed the other way; that was sampling noise.)
  • We are not claiming a chokepoint alone wins. A naive chokepoint (C) only ties free-form B. The win is specific: no single-call escape and a monitor that reads trajectories. Either without the other is not enough.
  • D needs a monitor with memory. The whole mechanism is that exfil must compose, so a monitor that reads trajectories is required — a purely per-call monitor is the wrong tool for this design, by construction.
  • A tidy sandbox. A synthetic canary, one benign task family, a closed environment. Whether the effect holds against a wider workload and a stronger monitor is the open question.

Why it matters

Transparency you can trust vs. transparency that lulls

Intent-labeled tools are widely assumed to aid oversight — you can read what the agent meant to do. This is evidence the same labels can lower a monitor's guard: a well-intentioned "make it legible" design can make misuse harder to catch. But the fix is constructive, and specific. Don't design tools to look trustworthy; design them so that the dangerous thing can't be done in one unremarkable call. Force it to compose — read, then stage, then send — and a monitor that watches trajectories reads the composition off the record. That is the property to engineer for, and it's checkable statically (is there an edge that lets data leave without composing?).

This result is robust for one small (8B) trusted monitor — exactly the cheap overseer that control setups assume. The obvious next tests are a stronger monitor and a wider workload.

Applying it

Designing tools a misaligned model can't quietly abuse

If oversight of a capable model rests on reading its tool calls, this turns into concrete design rules. The aim isn't to make a tool look safe — it's to make quiet misuse structurally have to show itself.

  • Leave no single-call escape. No one tool should both assemble and carry out a catastrophic effect — send arbitrary bytes outside, drop a dataset, move money — in one opaque call. If a single call can do it, there's no composition to read and nothing to catch. Make the dangerous effect take several steps.
  • Design for risk, not reassurance. A soothing name like export_data lowers a monitor's guard — and a human reviewer's. The call should foreground the risky fact (data is leaving, to an external place, of this kind), never a sanctioned-sounding label.
  • Let only real, named things leave. An egress tool should move typed sources — a specific file, record set, or object — not an agent-composed blob. Then anything reshaped or smuggled has to be staged first, a visible step, and every exit traces to something the system can name.
  • Give the overseer memory. Forcing composition only pays off if the monitor reads sequences, not single calls. Budget monitoring for trajectories, and concentrate it where data actually leaves.
  • Check it before you ship — statically. This is auditable at design time, and it's what this project's analyzer does: model the toolset as a capability graph and, for every catastrophic effect, report whether it is blocked, funnelled to one monitorable chokepoint, or left as a residual path that dodges oversight. It also counts single-call escapes — any tool that takes agent-controlled input straight to a catastrophic sink — which is what tells apart two designs that look identical on coverage: the chokepoint that still accepts fabricated content scores 1, the provenance-typed one that only exports real sources scores 0. Zero means every catastrophic effect must be composed. All of it computed before the model ever runs.

This isn't only about data theft. The same graph analysis treats the whole catastrophic set as source → sink effects — writing to the production database, reading credentials or secrets, touching model weights — not just exfiltration. In the toolset studied here (nine such effects), the opaque and free-form designs leave all nine residual; the chokepoint design blocks five outright (no tool can write prod, read secrets, or read weights) and funnels the remaining four through one door — zero residual. "Pushing to prod" is governed exactly the way exfiltration is: by ensuring there's no ungoverned path to the sink.

None of this makes misuse impossible — a determined model can still act — but it makes secret, one-shot misuse structurally hard, and turns "did it just do something bad?" into a question a monitor can answer. The design flaw at the heart of this note is itself catchable statically: the escape that lets a chokepoint be lulled shows up as a single-call escape the analyzer scores. What the graph can't tell you is whether the monitor will then actually look — so the static check is the necessary first gate, and a monitor that reads trajectories is the second.
